# Linear 工作流说明：逐页讲稿大纲

## 0. 开场：为什么要用 Linear

- 这不是 Linear 产品宣传，而是我们公司的协作方法说明。
- 真实工作不只发生在代码里，还包括机械安装、测试、会议、采购、人事、线下执行等。
- 现在最大问题不是没人干活，而是信息散、证据丢、后续 AI/同事接不上。
- 这套流程的目标：老板快速看状态，PM 能拆解同步，工程师和 AI 打开任务就知道下一步。

## 1. 第一部分：Linear 元素边界

- 先统一概念，不要把 Project、Milestone、Issue、Comment、Update 都叫“任务”。
- Team：部门/小组归属，决定权限和工作池，不是微信群。
- Project：项目方向和边界，写为什么做、做到什么程度、谁判断成败。
- Milestone：阶段验收点，不是任务篮子。
- Issue：最小执行闭环，最好一个负责人能推进，一个结果能判断。
- Comment：进展、证据、风险、下一步，不写长篇作文。
- Update / Done：Update 是阶段汇报，Done 是关闭依据，都要引用证据。

## 2. 从公司拆到一个极小 issue

- 这页讲“颗粒度”：越上层字段越完整，越下层越轻量。
- 公司层面管方向和资源，部门管能力边界，Project 管一个明确方向。
- Milestone 把大项目切成可验收阶段，Issue 落到具体可执行动作。
- 这样可以避免每个小任务都填一堆大项目字段。

## 3. 第二部分：小问题如何推进

- 日常最常见的不是大工程，而是某个具体卡点。
- 遇到小问题先建 issue，不要一上来建 Project，也不要只在聊天里散聊。
- 推进方式：建 issue → 短评论 → 必要时拆 subissue → Git Refs → Done 证据。
- 如果是非代码工作，也可以进 Linear，证据换成照片、视频、会议纪要、采购单、测试记录。

## 4. 小问题推进场景

- 建 issue：标题具体，目标、范围、验收能判断。
- 短评论：只写关键进展和证据；复杂推理放文档链接。
- 拆 subissue：能单独负责人、单独验收、单独关闭才拆。
- Git Refs：commit 写 `Refs TIM-xx: ...`，让代码和任务自动关联。
- Done 证据：关闭前留下结论、截图/日志/视频、commit、产物路径、后续链接。

## 5. 第三部分：部门内和部门间协作

- 部门内靠快速评论闭环，部门间靠显式依赖，不靠口头转发。
- 部门内：能在原 issue 评论解决的，不必乱拆。
- 部门间：用 related / blocked by / subissue 表达依赖。
- @ 人时要写清希望确认什么、给什么输入、是否影响验收。
- 评论 resolve 表示讨论点闭环，不等于 issue 完成。
- Linear issue 默认单 assignee，多人协作用主负责人 + subissue / 评论 @ 人表达。

## 6. 第四部分：验收、证据、Update

- 部门说完成了，老板未必知道为什么算完成；中间需要 PM 桥接。
- 部门验收看技术证据：能运行、误差、稳定性、实物安装、测试记录。
- 老板验收看业务结论：能否演示、是否交付、是否影响整体进度。
- Done 证据不是新任务，而是“为什么能关闭”的依据。
- Project Update 是阶段管理摘要，引用关键 issue，不复制 issue 全文。

## 7. 第五部分：风险、阻塞、延期

- 最大问题不是出问题，而是问题影响计划却没人提前看见。
- Risk issue：可能影响 Milestone、交付、成本、跨部门资源或老板决策的不确定性。
- Blocked：写清被什么卡住、等谁、需要什么输入、解除后下一步。
- Delay：延期不是只改日期，要写原因、剩余工作、新截止时间、是否影响上级 Milestone。
- 小问题先留评论；只有影响计划时才升级为 Risk issue。

## 8. 最后一部分：完整主线

- 用“新机械臂仿真闭环项目”把所有元素串起来。
- 老板提出目标 → PM 建 Project → 拆 Milestone → 建 Issues → 部门内推进。
- 跨部门问题拆 subissue，代码提交用 Refs，影响阶段的风险建 Risk issue。
- 老板验收看 Update 和关键证据，PM 把技术证据翻译成业务结论。
- Done 后保留结论、证据、commit、产物路径，后续方向进 Backlog 或新 issue。
- AI 工程师接手时，先读 issue 描述、最新评论、关联 commit；完成后留下交接说明。

## 9. 收束：这套流程到底解决什么

- 少重复解释：新人和 AI 不需要每次重新问背景。
- 少长篇作文：Linear 放结论和证据，复杂推理放链接。
- 少隐藏风险：影响计划的事情独立可见。
- 多可验收结果：Done 要能经得起未来复盘。

## 10. 结束语

- Linear 不替大家工作，它负责让工作不丢。
- 新项目从 Project 开始，小问题从 issue 开始。
- 跨部门依赖显式写出来，完成一定留证据。
- 先不要追求完美流程，先做到关键内容不丢，再根据真实使用继续调整。
